# Security design

Stern's security model in detail. The short version is in the README's
Security table; this page explains how the pieces fit and what they do
and do not defend against. The key hierarchy was decided in ADR-0003.

## Threat model

Stern defends against:

- **Vault file theft.** An attacker who obtains `stern.db` (stolen
  laptop, copied backup, cloud-synced folder) but neither the master
  password nor the unlocked device should learn nothing.
- **Casual device access.** Someone with the device but not the password
  faces the device Secret Key requirement plus unlock throttling.
- **Memory scraping of a locked vault.** Keys are zeroized on lock and
  kept out of swap while unlocked.

Stern does not defend against a fully compromised, unlocked machine
(malware running as the user while the vault is open). No local secrets
manager can; the design goal is to shrink that window (auto-clearing
clipboard, keys only in locked memory, lock on demand).

There is no server and no account, so there is no server-side breach
surface and nothing to phish. The single network operation in the
product — the AI model download — is integrity-protected by a pinned
SHA-256 (see [2026-11-21 - AI-and-Models.md](2026-11-21%20-%20AI-and-Models.md)).

## Unlock: two-secret key derivation (2SKD)

Unlocking requires two secrets:

1. The **master password** (something you know).
2. A 16-byte **device Secret Key** (something this device has), generated
   at vault creation and stored in the OS keychain via the `keyring`
   crate — macOS Keychain, Windows DPAPI, Linux Secret Service.

Derivation:

```
password + device Secret Key
  → HKDF-SHA256 preprocess (combines the two secrets)
  → Argon2id (256 MiB, 3 iterations, parallelism 4)
  → master key
  → HKDF-SHA256
  → KEK (key-encryption key)
```

![Two-secret key derivation (2SKD)](2026-11-21%20-%20Security%20-%20Key%20Hierarchy.png)

*Unlocking derives the KEK from two secrets, so a stolen database alone cannot be brute-forced at full speed — the attacker also needs the device Secret Key.*

Consequences: a stolen database alone is not enough to brute-force the
password offline at full speed — the attacker also needs the Secret Key
from the device's keychain — and a guessed password on another device
fails without the keychain entry. Losing both the password and the
device means the vault is unrecoverable. That is deliberate: there is no
reset flow to attack.

Parameters live in `domain/vault/kdf_params.rs` and
`domain/vault/crypto_constants.rs`. Do not weaken them without a new ADR
and a migration story for existing vaults.

## Entry encryption

Every entry is encrypted independently:

- On each write, a **fresh random DEK** (data-encryption key) is
  generated for that entry.
- The entry's fields are encrypted with **XChaCha20-Poly1305** (AEAD).
  The associated data binds the ciphertext to its context (vault and
  entry identity, constructed in `domain/vault/aad.rs`), so ciphertext
  cannot be transplanted between entries or vaults without detection.
- The DEK is **wrapped with AES-KW (RFC 3394)** under the KEK and stored
  alongside the ciphertext.

Per-entry keys limit the blast radius of any single-key compromise and
make re-encryption on password change cheap: only the wrapped DEKs need
re-wrapping, not every entry's contents.

## Verification before decryption

`VaultMeta` stores a verification hash of the derived key material.
Unlock compares it in **constant time** and fails before touching any
entry if the password (or Secret Key) is wrong. Failed unlock attempts
are throttled in the shell, so online guessing against a running app is
rate-limited on top of Argon2id's cost.

## Memory hygiene

- Keys and plaintext secrets are held in `SecretMem<T>`, which `mlock`s
  its pages (no swap) and `zeroize`s on drop.
- The session exists only while the vault is unlocked; locking drops it.
- The clipboard integration (arboard) sets platform exclusion hints so
  copied secrets stay out of clipboard history where the OS supports it,
  and auto-clears after use.

## Chat is not a secret channel

Chat exists to navigate the vault, not to carry secrets:

- The classifier sees the user's sentence, never a secret value — store
  flows collect the secret in the entry form.
- For vault actions, the chat response suppresses the echoed user
  message (`user_message_display` is cleared), so a stray pasted secret
  is not rendered back or kept in the transcript.
- Destructive actions (delete) go through explicit confirmation UI, not
  the classifier's say-so (ADR-0005).

## Storage

The vault is a single SQLite file (`stern.db`) holding ciphertext,
wrapped DEKs, and the minimal metadata needed to derive and verify keys.
Copying the file copies the vault — which is why the encryption above,
not file permissions, is the security boundary. Encrypted export/import
(`infrastructure/backup.rs`) is the supported way to move a vault
between devices, together with the Secret Key from the keychain.
